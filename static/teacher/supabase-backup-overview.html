Supabase Free Has No Backups — Here's the Free Way to Add Them

2026-11-13 · 五个坑总览 · Backup Kit 系列首篇 · 原文首发

If your side project lives on a Supabase Free project, here is the uncomfortable fact: there are no automated backups. None. If you drop the wrong table tonight, there is no restore button waiting for you in the dashboard tomorrow. The fix Supabase sells you is the Pro plan at $25/month — mostly, for a lot of us, just to get daily backups retained for 7 days.

The DIY fix looks trivial: run pg_dump from a GitHub Actions cron job, upload the result somewhere cheap. It is about 30 lines of YAML. But those 30 lines hide five traps, and every one of them fails quietly — you find out your backup doesn't work on the one day you actually need it.

I hit all five while building my own setup. Here they are, in the order you'll meet them.

Trap 1: The connection string Supabase shows you first breaks pg_dump

In the dashboard (Settings → Database → Connection string), the prominent option is the transaction pooler on port 6543. pg_dump cannot run through it — it needs a real session, and through the transaction pooler the dump fails or hangs with errors that point nowhere near the real cause.

Use the session pooler instead: port 5432, host aws-0-<region>.pooler.supabase.com. Same panel, different tab. This one line is the difference between a working backup and a week of debugging.

Trap 2: The "direct connection" is IPv6-only, and GitHub runners are not

The other string in the dashboard, db.<your-ref>.supabase.co, looks like the obvious choice for a dump. On the Free plan that host is IPv6-only. GitHub-hosted runners are IPv4-only. The result is a connection error that looks exactly like a firewall or credentials problem — it is neither. (This is also why the same string works fine from your laptop on an IPv6 network and fails in CI.)

Session pooler, port 5432. Again. Traps 1 and 2 are the same lesson: the two connection strings Supabase offers first are the two that don't work.

Trap 3: Your pg_dump is older than the server

Supabase runs PostgreSQL 17. The ubuntu-latest GitHub runner ships a PostgreSQL client that tops out at 16 — and pg_dump flatly refuses to dump a server newer than itself:

pg_dump: error: server version mismatch

postgresql-client-17 isn't in Ubuntu's default repos, so the fix is to add PostgreSQL's official PGDG apt repository first, then install the 17 client. Three extra lines in the workflow — once you know you need them.

Trap 4: GitHub silently disables scheduled workflows in public repos

This is the nastiest one because nothing ever errors. If your backup repo is public and sees no activity for 60 days, GitHub disables scheduled workflows — quietly. No failed run, no red X, just backups that stop happening while you believe you're covered.

Put the backup workflow in a private repo. (You want this anyway: the repo holds your database connection string as a secret and your backup config.)

Trap 5: Daily backups blow straight through the Free egress cap

Every dump pulls your entire database out of Supabase, and the Free plan includes 5 GB/month of egress. The math is unforgiving:

  • 500 MB database, dumped weekly → ~2 GB/month. Fine.
  • 500 MB database, dumped daily → ~15 GB/month. Over the cap.

Weekly is the sweet spot on Free. And double-check your cron while you're at it: 42 3 * * 0 is weekly (Sundays 03:42 UTC); drop the trailing 0 and 42 3 * * * quietly becomes daily — trap 5, self-inflicted.

One honest scope note: pg_dump covers your database, including auth.users (they live in the database). It does not cover Storage files — those live in S3, not Postgres, and need a separate approach. Anyone who tells you their pg_dump setup protects "everything" hasn't checked.

The free version: the smallest thing that actually works

Once you know the five traps, the working minimum fits in one workflow:

  1. GitHub Actions cron, weekly, in a private repo
  2. Install postgresql-client-17 from the PGDG repo
  3. pg_dump over the session pooler (5432), custom format
  4. Upload to a Cloudflare R2 bucket (10 GB free tier, zero egress fees)
